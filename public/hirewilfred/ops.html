Control plane — clients never touch this

  • Onboarding portal + provisioning service
  • Control-plane Postgres (client records, config)
  • Vultr API key, scoped, in a secrets manager
  • Terraform state — remote backend, locking on from day one
  • Usage/metering and billing tables
  • Alert webhooks and cap thresholds

Tenant plane — client data only

  • Per-client agent containers
  • Per-client Postgres schema or instance
  • Client admin logins and user invites
  • Subdomain: clientname.hirewilfred.ca
  • No credentials that reach any other tenant
Keep these two planes separate. Blurring them is the mistake that turns one compromised container into a platform-wide breach. A leaked Vultr key deletes every client server you have; corrupted Terraform state means you can no longer manage what you provisioned; and half-provisioned clients from a failed run are the number-one source of onboarding chaos — every step must be safely re-runnable.

      Self-hosting — the trigger, not the temptation

      Don't build it now. Pull the trigger only when all three of these are true at once:

        Start with a fractional L40S serving only Wilfred's routing traffic — the smallest possible bet, real data, no client-visible risk. Use vLLM rather than Ollama; continuous batching is what makes multi-tenant concurrency viable. VPC peering only, no public IP on the GPU box, per-tenant API keys with rate limits. Size for peak concurrency, not average.

        Hybrid routing — what runs where

        The move is routing, not replacement. High-volume, low-stakes work goes cheap; anything a client sees stays on the quality model. If the local model underperforms you flip a config value per agent, not rebuild.

        What this breaks — say it out loud in the security questionnaire. A shared inference box reintroduces a component every tenant's prompts flow through, which partly undercuts the no-lateral-movement story of per-client isolation. Mitigate with stateless inference, no prompt logging and per-tenant keys. It is also a single point of failure — GPU down means every client down — so plan fallback-to-Claude-API on inference failure. Sovereignty gets stronger, though: nothing leaves your infrastructure at all, which is the strongest version of the pitch for Ontario law and insurance.

        On open-weight models: running them through someone else's API sends client data off your infrastructure and contradicts the PIPEDA/sovereignty positioning the whole pitch rests on. If you go open-weight, self-hosting stops being a cost optimisation and becomes a requirement. Check the licence before you benchmark — Apache 2.0 and MIT are resale-safe, custom licences are not a footnote when you're reselling. And benchmark on your own agent traces, not leaderboards: start with Wilfred's routing traffic only, keep client-facing legal and insurance reasoning on the quality model until your own eval says otherwise.
